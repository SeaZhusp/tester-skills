# 04 · 计数口径与换算（Counting & Conversion）

> **核心结论：售前预估口径 = 交付口径。**
> 两条路径都从同一份 Spec Model、用同一段代码（`scripts/count_cases.py`）得出条数。

---

## 1. 计数方法：枚举，不是估算

条数**不能由公式相乘得出**，只能由场景枚举得出。

**为什么乘法一定不准**：`用例数 = 功能点 × 每功能点条数` 这种写法，把"一条用例承载几个测试点"当成了常数。
但聚合度是**设计变量**——同一个模块，可以设计成 12 条粗粒度用例，也可以设计成 90 条细粒度用例，两者都覆盖同样的需求。
既然聚合度不是常数，任何"× N 条"的乘法都只是在给一个可变量硬套固定值，误差无法收敛。

**本套件的做法：模拟计数（dry-run count）**——在 Spec Model 上把生成逻辑"虚跑一遍"，只数不写。
售前与交付调用**同一段代码**，因此两者之间不存在"两套口径"这个可能性，偏差恒为 0（除非中途改了范围）。

---

## 2. 计数口径

### 2.1 唯一计量单位
`一条用例 = 一个可独立执行的业务操作场景`（定义见 `02-case-granularity-contract.md`）。

### 2.2 计数来源

```
待估条数  ==  python3 "$SKILL_DIR/scripts/count_cases.py" spec-model.json 的输出
```

**禁止**：
- 手写条数；
- 在报告/配置里另设倍率或经验比例；
- 跳过 Spec Model 直接从需求文档数数。

### 2.3 计数范围

| 计入 | 不计入 |
| --- | --- |
| 功能用例（模块 scenarios 枚举结果） | 纯 UI 样式/文案断言（无业务语义） |
| 非功能需求（`non_functional[]` 的 `cases_hint`） | 文档缺口占位（默认**单列**，见第 3 节） |
| 跨模块端到端主流程（作为冒烟来源，已在场景中计数的不重复） | 重复覆盖的去重差额（已在 `dedup_log` 登记） |

---

## 3. 三档区间的来源：枚举结果 ± 未决项

三档**不是**把基准乘以 0.8 / 1.2，而是把"已确认范围"与"未决范围"分开加总，来源可解释：

| 档 | 计算方式 | 用途 |
| --- | --- | --- |
| **保守（min）** | 基准 − `gaps` 中 `included_in_baseline=true` 的占位条数 − 跨模块集成场景 | 风险自留报价、正式承诺下限 |
| **基准（typical）** | `count_cases.py` 全部枚举结果（含已确认范围） | **默认推荐口径**，合同基准 |
| **激进（max）** | 基准 + `gaps` 全部占位（按补齐后估算）+ 跨模块集成/契约场景 + 非功能加点 | 评估最大工作量、上限报价 |

**要点**：三个数的差异**必须有具体来源**（哪些模块属于未决项），而不是"乘以 0.8 / 1.2"。报告中必须逐条列出未决项。

---

## 4. 冒烟用例

- 冒烟用例 = **端到端 L0 核心主场景** + 关键模块的 P0 happy path。
- 冒烟占比基准 **10%**，合理区间 **8% ~ 15%**（`assets/estimate-config.json` 的 `smoke_ratio` / `smoke_ratio_range`）。
- 占比明显偏离区间时：
  - 偏高 → 可能漏了大量普通用例（枚举不完整）；
  - 偏低 → 可能漏了核心端到端主流程。
- 冒烟用例**必须显式列出**，不允许只给个数。

---

## 5. 优先级分布：真实统计，不预设比例

优先级**由 Spec Model 的 `scenarios[].priority` 逐条统计**得出，推导规则见 `05-priority-taxonomy.md`。

- 计价按优先级定价，因此优先级分布直接决定总价，**不能先定比例再套到用例上**。
- `assets/estimate-config.json` 不存优先级比例（见 `05` 第 3 节），所以不存在"与参考值比对"这一步；分布是否合理按 `05` 第 2 节的定性约束判断（P0 占比 5%~35%）。
- 报告必须给出 P0/P1/P2/P3 的真实条数与占比，不得只给总数。

---

## 6. 工作量换算

### 6.1 产能参数必须按聚合口径标定

产能参数（条/人天）与用例粒度**强耦合**，两者必须同时定义：

- 一条聚合用例承载 2~4 个测试点，含多组步骤/预期，设计与执行耗时都是细碎用例的 3 倍量级。
- **若产能按细碎用例标定（一条用例一个校验点），人天会被系统性低估约 3 倍**，报价随之失真。
- 因此本套件的产能参数**只能按聚合用例口径**取值，不得跨口径复用。

### 6.2 参数取值与依据（见 `assets/estimate-config.json`）

| 参数 | 取值 | 依据 |
| --- | --- | --- |
| `case_design_per_day` | 120 | 聚合用例含多组步骤/预期 + 前置条件；且需从 Spec Model 落地为可读文本 |
| `case_execution_per_day` | 45 | 一条用例含多个校验步骤，执行耗时上升 |
| `regression_per_day` | 60 | 回归只跑缺陷修复相关步骤，略快于首轮 |

> 参数是**经验初值**，首次交付后由 `qa-audit-engine` 校准回填（见第 8 节）逐步修正为项目实测值。

### 6.3 阶段换算（由 `scripts/estimate.py` 计算）

| 阶段 | 公式 |
| --- | --- |
| 需求分析与用例设计 | `总用例 ÷ case_design_per_day` |
| 用例评审 | `设计 × review_ratio`（默认 0.20） |
| 测试环境与数据准备 | `max(1.0, 设计 × env_prep_ratio)`（默认 0.10） |
| 用例执行（首轮） | `总用例 ÷ case_execution_per_day` |
| 缺陷回归测试 | `总用例 × regression_scope_ratio ÷ regression_per_day`（默认 0.30） |
| 测试报告与收尾 | `report_days`（默认 1.0） |
| **合计** | 上述之和 × `(1 + buffer_ratio)`（默认 0.15） |

**周期与人数**：
- 给定人数：`周期(自然日) = 含缓冲人天 ÷ (人数 × parallel_efficiency)`，`parallel_efficiency` 默认 0.90
- 给定周期：`人数 = ceil(含缓冲人天 ÷ (周期 × parallel_efficiency))`

## 7. 报价换算

- 计价按优先级（P0 最贵）或按测试类型，方案与单价见 `assets/pricing-config.json`。
- **条数必须来自真实统计**（`count_cases.py` 输出 + 真实优先级统计），不得使用拍出来的分布。
- 报告必须同时给出：**统计明细 + 计价明细 + 总价**，且统计合计 = 计价条数合计（由 `check_consistency.py` 核验）。

---

## 8. 校准回填（闭环，非可选）

交付完成后，`qa-audit-engine` 必须执行校准：

1. 记录**实测聚合比** = 实际测试点数 ÷ 实际交付用例数。
2. 与预估聚合比对比，偏差 > 20% 时给出**参数修正建议**（调整 `case_design_per_day` 等）。
3. 修正建议**不自动写入** `assets/`，需经用户确认后由总控统一修改（遵守"配置唯一"契约）。

**闭环的意义**：偏差被度量、被解释、被收敛，而不是靠"下次估准一点"。

---

## 9. 反例（禁止出现的写法）

| 禁止 | 原因 |
| --- | --- |
| "功能点数 × 每功能点 N 条 = 总数" | 把聚合度当常数，条数不可核销 |
| "按 P0 15% / P1 30% 拆分" | 与真实优先级分布冲突，直接扭曲报价 |
| "保守 = 基准 × 0.8，激进 = 基准 × 1.2" | 差异无来源，不可解释 |
| "按细碎用例口径标定产能（如 300 条/人天）" | 与聚合用例口径不匹配，人天低估约 3 倍 |
| "评估报告只给总数" | 缺模块级明细，不可追溯、不可核销 |
| "使用 `assets/` 之外的参数值" | 违反配置唯一契约，导致同一套件内数字互相矛盾 |
