# 01 · 需求解构规约（Requirement Decomposition）

> 职责：把一份需求文档（PRD / 原型 / 接口文档 / 用户故事）**确定性地**拆成
> `模块 → 功能点 → 测试点 → 场景` 四级结构，落成 Spec Model。
> **先结构化，后估算，绝不"边读边估"。**

---

## 1. 解构总流程（严格顺序，禁止跳步）

```
Step 1  建立完整模块索引（只扫标题/目录/图号/接口清单，不读正文细节）
Step 2  逐模块提取功能点（先清单，后定级）
Step 3  逐功能点铺开测试点（正向/边界/异常/状态/权限 五类）
Step 4  按场景枚举规则生成场景（见 02-case-granularity-contract.md 第 3 节）
Step 5  跨模块去重并登记 dedup_log
Step 6  结构机检（validate_spec_model.py 必须 PASS）
```

**为什么必须分步**：一次性把大文档读进上下文再估算，会因上下文稀释与注意力衰减导致**系统性漏项**（后面的章节被忽略、跨模块场景被简化）。分步是为了每个模块都获得同等的注意力预算。

---

## 2. Step 1 · 模块索引

### 判定：什么是一个"模块"

> **模块 = 文档中的一个可独立交付/可独立验收的功能单元**，通常对应一级或二级标题、或一个独立页面/接口分组。

强制要求：
- 索引必须覆盖文档的**每一个章节**，不允许"这部分不重要跳过"。
- 大文档（> 50 页）**分批读取**，但索引表**一次建全**。
- 每个模块记录：`模块名 / 章节号 / 是否含界面 / 是否含接口 / 是否含状态流转 / 是否含权限`。

**产出**：Spec Model 的 `modules[]`。

---

## 3. Step 2 · 功能点提取与复杂度定级

### 3.1 功能点判定

> **功能点（Feature Point）= 一个可独立验证的业务能力**
> （如"新增用户""修改订单状态""导出报表""审批通过"）。

判定标准：**至少能对应一条可执行、可断言的测试用例。**

**不是功能点**：字段、按钮、提示语、纯展示元素。

### 3.2 复杂度定级判据（唯一权威，全链路共用）

> ⚠️ **重要**：复杂度定级**不参与用例条数的换算**（条数由场景枚举得出，见 `02` 与 `04`）。
> 定级的用途只有两个：**(a) 报价加权；(b) 风险提示与覆盖优先级**。

| 档位 | 判据（满足任一条即达该档；同时满足多条时**取最高档**） |
| --- | --- |
| **简单 simple** | 单一页面/接口/动作；可编辑字段 ≤ 2；无状态流转；无角色语义差异；无外部依赖 |
| **中等 medium** | 可编辑字段 3~5；或分支逻辑 2~3；或存在状态流转；或 1 类角色语义差异；或单个外部依赖 |
| **复杂 complex** | 可编辑字段 > 5 或含多步骤向导；或状态机 > 3 个状态；或多角色权限；或跨模块联动；或涉及金额/库存等关键数据；或多数据源；或含回滚/补偿逻辑 |

**定级纪律**：
1. 逐功能点**独立定级**，不允许"整体拍一档"。
2. 定级结果必须写入 Spec Model（`complexity` 字段），不得只停留在中间推理。
3. 无法判定时**取较低档**，并在 `assumptions` 中登记（宁可低估风险，不可虚高报价权重）。
4. 定级是主观的，因此必须接受 `02` 第 4 节的**区间反查自检**与 `qa-audit-engine` 的抽样复核。

---

## 4. Step 3 · 测试点铺开（五类维度）

每个功能点按下列五类铺开为测试点（TestPoint）：

| 类别 | 铺开规则 | 典型产出 |
| --- | --- | --- |
| **正向** | 主流程 1 个；存在入口/角色/数据特征分支时，每分支 +1 | `可正常新增用户` |
| **边界** | 每个可编辑字段/参数 2~3 个（下界-1 / 下界 / 上界 / 上界+1），**只在字段有明确约束时铺** | `用户名长度=3（下界）` |
| **异常** | 按异常注入：必填缺失 / 格式非法 / 超长 / 依赖失败 / 重复提交；关键功能点 2~4 个 | `必填字段缺失时提交` |
| **状态** | 每个合法状态转移 1 个；每个非法/越权转移 1 个 | `已完成任务不可重跑` |
| **权限** | 每个角色的可执行性差异 + 越权访问 1 个 | `普通用户访问管理员页面` |

**铺开的产出是"测试点"，不是"用例"。** 测试点后续会被 `02` 的聚合规则合并进用例，聚合比目标 `[1.5, 4.0]`。

### 测试点编号规范

```
TP-<模块短码>-<序号>
例：TP-CV-001（看板）、TP-RPT-012（测试报告）、TP-LOGIN-003（登录）
```

---

## 5. Step 4 · 场景枚举

严格按 `02-case-granularity-contract.md` 第 3 节的四抓手（入口 / 动词 / 状态转移 / 角色差异）枚举。

**这里只做枚举，不写用例文本。** 枚举出的场景进入 Spec Model 的 `scenarios[]`，其 `point_ids` 字段回填该场景承载的测试点。

---

## 6. Step 5 · 跨模块去重

识别跨模块重复覆盖的内容并去重（规则见 `02` 第 5 节），差额登记进 `dedup_log`。

**要求**：`dedup_log` 必须逐条写明「去重对象 + 保留位置 + 原因」，否则视为漏登记。

---

## 7. Step 6 · 遗漏检查清单（收尾前逐项核对）

- [ ] 模块索引覆盖 PRD **每一个章节**（无跳过）？
- [ ] 每个功能点都有正向 + 异常测试点？（有约束的字段才有边界）
- [ ] 每个有约束的输入字段都有边界值测试点？
- [ ] 每个核心业务对象（订单/用户/任务/看板/审核单…）都有状态机覆盖（含非法转移）？
- [ ] 每个角色都有权限与越权测试点？
- [ ] 每个跨模块依赖都有集成/契约测试点？
- [ ] 高风险点（金额/库存/权限/审核/并发）有专项异常覆盖？
- [ ] 非功能需求（性能/安全/兼容/并发）单独列出并纳入？
- [ ] 每个功能点都有复杂度定级，且 `assumptions` 已登记无法判定的项？
- [ ] `dedup_log` 已登记所有去重差额？
- [ ] `validate_spec_model.py` 已 PASS？

---

## 8. 假设与置信度（必须显式输出）

解构结束时必须登记：

- **假设清单 `assumptions`**：解构依赖的关键假设（如"接口文档齐全""无性能专项""某章节正文缺失，按占位处理"）。
- **文档缺口 `gaps`**：正文缺失、描述简略、附件缺失的章节，逐条列出并标注影响范围。
- **置信度 `confidence`**：
  - `high`：文档清晰、功能点可枚举、无缺口；
  - `medium`：部分章节模糊或有缺口但不影响主体；
  - `low`：文档严重缺失，需访谈补全。

**缺口必须影响区间估计**：`gaps` 中的占位模块，在评估时单列为"待澄清，未计入基准"（见 `04` 第 3 节）。

---

## 9. 解构阶段的常见错误

| 错误 | 表现 | 后果 | 正确做法 |
| --- | --- | --- | --- |
| 边读边估 | 读一半就给总数 | 后段章节系统性漏项 | 先建完整模块索引，再逐模块铺开 |
| 用乘法代替枚举 | "功能点数 × 每功能点 N 条" | 聚合度被当常数，条数不可核销 | 按第 5 节逐场景枚举 |
| 无视文档缺口 | 正文缺失的章节仍按正常模块估 | 报价虚高，交付争议 | 登记进 `gaps[]`，三档区间中单独体现 |
| 跳过去重 | 同一操作在 3 个模块各计一次 | 条数虚高 | 按第 6 节跨模块去重并登记 `dedup_log` |
| 定级不留痕 | 复杂度只存在于推理过程，没写进产物 | 无法复核、无法校准 | 逐功能点写入 Spec Model |
