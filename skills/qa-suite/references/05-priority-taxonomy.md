# 05 · 优先级体系（Priority Taxonomy）

> **唯一权威。** 用例生成、统计、售前评估、报价四方共用本表。
> **核心规则：优先级由场景本身客观推导，不按预设比例分配。**
> 为什么不能按比例分配：比例是预先设定的，与这条场景真实的业务风险无关；而计价按优先级定价，
> 一旦优先级失真，报价就同步失真，且失真的方向不可预测（既可能高估也可能低估）。

---

## 1. 四档定义

| 档位 | 名称 | 定义 | 判定要点 |
| --- | --- | --- | --- |
| **P0** | 阻塞/冒烟级 | 不通过则系统核心业务不可用，**属于冒烟集** | 端到端核心主流程；关键模块的 happy path |
| **P1** | 重要 | 核心业务规则、关键异常与关键权限/状态，影响主要功能可用性 | 重要业务规则的正向 + 关键异常；金额/库存/权限/审核类校验 |
| **P2** | 一般 | 常规功能与常规异常、一般边界 | 普通 CRUD 的异常分支；常见边界值 |
| **P3** | 边缘 | 极端边界、体验类、低频路径 | 极值、超长输入、罕见组合、文案与体验 |

---

## 2. 推导规则（从场景客观推导，不拍比例）

按下列顺序判定，**命中即定档**（取最高命中档）：

| # | 条件 | 档位 |
| --- | --- | --- |
| R1 | 场景属于**端到端 L0 核心主流程**（跨模块串联主链路） | **P0** |
| R2 | 场景是**关键模块**（被标记 `key_module=true`）的正向 happy path | **P0** |
| R3 | 场景涉及**核心业务规则**的正向验证（状态机合法转移、审核通过、支付成功等） | **P1** |
| R4 | 场景涉及**关键异常**：金额/库存/权限/审核/并发冲突/回滚补偿 | **P1** |
| R5 | 场景是**权限/越权的核心分支**（角色不可见、越权访问被拒） | **P1** |
| R6 | 场景是普通功能的常规异常分支（必填缺失、格式非法） | **P2** |
| R7 | 场景是常规边界值（长度上下界、数值上下界+1） | **P2** |
| R8 | 其余（极端边界、超长、罕见组合、体验类） | **P3** |

### 推导纪律

1. **逐场景推导**，不允许整个模块拍一档。
2. 推导结果写入 Spec Model 的 `scenarios[].priority`。
3. **P0 必须有下限与上限约束**：
   - P0 占比过低（< 5%）→ 疑漏核心主流程；
   - P0 占比过高（> 35%）→ 疑滥标 P0（"什么都重要"等于都不重要）。
   - 该区间由 `count_cases.py` 输出优先级分布时直接给出告警（`p0_check`），**不强制**、不阻断门禁。
4. 冒烟用例 = **P0 集合**（含端到端 L0 主场景）。两者天然一致，不允许分别给出不同集合。

---

## 3. 配置里不设优先级比例

`assets/estimate-config.json` **不存任何优先级比例**，优先级只存在于 Spec Model 的 `scenarios[].priority`。

**为什么配置里不能有比例**：比例一旦可查，就会被当成目标去凑——先有"P0 应占 15%"的配额，再去找 15% 的场景填进去。
这与"按业务风险逐条定级"直接冲突，而计价按优先级定价，凑出来的分布会系统性搬动报价。

分布是否合理，只用第 2 节的定性约束判断（P0 占比 5%~35%），**不做"与参考比例比对"**：
比对参考比例，本质仍是让一条预设数字去校正真实判断。

---

## 4. 优先级在三个环节的用法

| 环节 | 用法 |
| --- | --- |
| 用例生成 | 决定 Excel 配色与排序；决定是否进入冒烟集 |
| 售前评估 | **真实统计**得出 P0~P3 分布，用于周期与风险呈现 |
| 报价 | 按优先级计价（P0 单价最高）；条数必须来自真实统计 |
