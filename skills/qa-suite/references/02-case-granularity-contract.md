# 02 · 用例粒度契约（Case Granularity Contract）

> **本文件是整个套件最重要的规则。** 它定义"一条用例"是什么。
> 售前评估、用例生成、报价、核销四方**全部使用本定义**，不允许任何一方另立口径。
> 为什么必须由一份文件定义：只要有一方按自己的理解切分用例，条数就在源头分叉——
> 同一份需求可以数出 12 条，也可以数出 107 条，两者都能自圆其说。计量单位不唯一，后续所有数字都失去意义。

---

## 1. 计量单位定义

### 1.1 正式定义

> **一条用例（TestCase）= 一个可独立执行的业务操作场景。**
> 判定三元组唯一：`（操作主体）+（业务动词）+（业务宾语）`。

满足以下**全部**条件才算一条用例：
1. **可独立执行**：不依赖另一条用例的执行结果即可发起（仅需前置条件）。
2. **场景完整**：包含完整的"发起 → 操作 → 可观测结果"闭环。
3. **可独立判定**：有明确的通过/失败结论。
4. **单业务意图**：只验证一个业务意图（但可包含该意图下的多个校验维度）。

### 1.2 什么**不是**一条用例（禁止单独成条）

| 不单独成条的内容 | 应归入 |
| --- | --- |
| 单个字段的必填校验 | 所属操作场景用例的**一个步骤** |
| 单个边界值（上界/下界/越界） | 所属操作场景用例的**一个步骤** |
| 单个格式非法输入 | 所属操作场景用例的**一个步骤** |
| 同一操作的权限差异 | 所属操作场景用例的**一个步骤**（或按第 4 节规则单独成条） |
| 同一操作的状态前置差异 | 所属操作场景用例的**一个步骤** |
| 纯 UI 样式/文案断言（无业务语义） | **不单独立用例**，作为所属用例的预期片段 |

### 1.3 步骤与预期的成对要求

一条用例内可以有多组校验，但**步骤与预期必须一一对应**（第 N 步 ↔ 第 N 条预期）。
多维校验合并写入同一条用例的多个步骤对，这是**契约要求**，不是风格偏好。

## 2. 聚合规则：测试点 → 用例

Spec Model 中存在两个层级的量，必须分清：

| 量 | 定义 | 用途 |
| --- | --- | --- |
| **测试点（TestPoint）** | 一个可独立判定的验证点（一条业务规则/一个边界/一个状态转移/一个权限差异） | 覆盖率度量、追溯锚点 |
| **用例（TestCase）** | 一个可独立执行的业务操作场景，**承载 1~N 个测试点** | 交付、执行、报价计数的**唯一单位** |

**聚合规则**：

```
一个操作场景（用例）  ←承载—  N 个测试点（N = 该场景下需要校验的维度数）
```

- 目标聚合比 **`测试点数 ÷ 用例数 ∈ [1.5, 4.0]`**。
- 比值 **< 1.5** → 疑过度拆分（把校验维度单独成条了），应合并。
- 比值 **> 4.0** → 疑过度聚合（一条用例塞了多个业务意图），应拆分。
- 该比值由 `scripts/check_consistency.py` 自动核验，超出区间直接告警。

## 3. 场景枚举规则（可数、可审计）

用例条数**由枚举得出，不由公式推算**。按下列 4 个抓手逐条枚举，枚举结果即 Spec Model 的 `scenarios`。

### 抓手 A：入口 / 页面
- 每个**独立页面或独立子页签** = 1 条"进入并正确渲染"用例。
- 同一页面的不同**进入路径**（不同入口/不同来源模块跳入）差异显著时，每个额外入口 +1 条。

### 抓手 B：业务动词（主力来源）
- 从需求文档提取**业务动词**（新增/编辑/删除/启用/停用/导入/导出/复制/提交/审核/发布/重跑/分配/解冻…）。
- `<动词> × <宾语>` 唯一组合 = 1 条用例。
- **同一动词 × 同一宾语，不论多少个字段或校验维度，只算 1 条**（维度落入步骤）。

### 抓手 C：状态转移
- Spec Model 中每个**合法状态转移** = 1 条用例。
- 每个**非法 / 越权 / 竞态转移** = 1 条异常用例。
- 状态转移已在抓手 B 中作为动词覆盖时**不重复计数**（去重规则见第 5 节）。

### 抓手 D：角色差异
- 同一操作在**不同角色下呈现不同结果**（不可见 / 只读 / 可编辑 / 数据范围不同）：
  - 仅在**权限语义变化**时 +1 条；
  - 仅数据范围不同（写作业完全一致）时**不单独成条**，作为该用例的一个步骤。

### 枚举公式

```
模块用例数 = A(入口数)
           + B(动词 × 宾语 唯一组合数)
           + C(未在 B 中覆盖的状态转移数，含非法转移)
           + D(未在 B 中覆盖的角色语义差异数)
           − 去重数（见第 5 节）
```

## 4. 常规场景数参考（用于自检，不作为计数依据）

枚举后可用下表**反查是否离谱**（仅自检，最终以枚举结果为准）：

| 模块类型 | 典型用例数 | 构成 |
| --- | --- | --- |
| 纯查询列表页 | 2 ~ 4 | 进入渲染 / 多条件筛选 / 排序分页 / 跳转详情 |
| 标准 CRUD 模块（单表） | 5 ~ 8 | 列表 / 新增 / 编辑 / 删除 / 启停 / 权限 |
| 含导入导出的 CRUD | 7 ~ 11 | 上述 + 导入（覆盖/忽略）/ 导出 / 模板下载 |
| 多页签管理模块 | 8 ~ 14 | 每个页签 2~4 条 + 页签间联动 |
| 画布 / 编排类交互 | 8 ~ 15 | 节点增删改 / 连线 / 复制粘贴 / 导入导出 / 生成 |
| 状态机类（订单/审核/任务） | 6 ~ 12 | 每个合法转移 1 条 + 关键非法转移 1~3 条 |
| 权限 / 角色管理 | 4 ~ 8 | 角色 CRUD / 菜单权限 / 操作权限 / 数据权限 / 越权 |

**若枚举结果显著超出该区间**：检查是否把校验维度单独成条了（违反 1.2）。
**若显著低于下限**：检查是否漏了入口、动词或状态转移。

## 5. 去重规则

1. **状态转移 vs 动词**：同一转移若已由"某动词"覆盖（如"启用角色"既是动词也是状态转移），只计 1 次，归到抓手 B。
2. **跨模块重复**：同一操作在多模块文档中重复描述（如"新增应用"在应用管理与其他模块都出现），只在**主归属模块**计数，其余模块用 `related_modules` 引用，不重复计数。
3. **角色差异 vs 权限模块**：各业务模块的角色可见性差异，若已在"角色权限管理"模块集中覆盖，业务模块不再重复计数，仅在该用例步骤中引用。
4. 去重后的差额必须在 Spec Model 的 `dedup_log` 中**逐条登记**（去重对象 + 保留位置），否则视为漏登记。

## 6. 聚合比区间 [1.5, 4.0] 的依据

区间不是经验拍的，由两条设计约束夹出来：

| 边界 | 推导 | 违反后的后果 |
| --- | --- | --- |
| **上限 4.0** | 一条用例的可执行长度上限约 12 个步骤对；单场景下需要校验的维度通常不超过 3~4 个，留 1 个余量 → 4.0 | 超过即一条用例塞了多个业务意图，失败后定位不到具体缺陷，回归也无法只跑受影响部分 |
| **下限 1.5** | 低于 1.5 意味着一半以上的测试点各占一条用例，即"一个字段校验一条用例" | 用例数膨胀、执行成本反升，且步骤高度重复，评审无法逐条读完 |

- **稳定带 [2.0, 3.0]**：设计目标，命中即认为该模块粒度正常。
- **超出区间不是错误，是需要解释的信号**：必须在该模块的 `note` 或核销报告中写明为什么合理（如画布交互天然需要多维度校验）。

首个项目交付后，`qa-audit-engine` 会用实测聚合比校准这一区间（见 `04` 第 8 节）。

## 7. 对生成侧（`qa-case-engine`）的强制要求

1. `title` 必须用 `【测试点类】测试目的` 格式，**测试目的是业务动作**，不写操作过程。
2. 一条用例的 `point` 字段可引用多个测试点编号（逗号分隔），这是**契约允许且鼓励**的。
3. **禁止**为单个字段校验、单个边界值、单个错误提示单独建立用例。
4. 若某模块按本契约枚举出的条数与 `count_cases.py` 输出不一致，**以 `count_cases.py` 为准**，并回头修正 Spec Model 的测试点归属。

## 8. 对评估侧（`qa-estimate-engine`）的强制要求

1. 预估条数**只能**来自 `scripts/count_cases.py` 对 Spec Model 的输出，禁止手写、禁止另设倍率。
2. 报告中必须给出三条数：**保守（min）/ 基准（typical）/ 激进（max）**，其来源为
   Spec Model 的枚举结果 ± 未决项（见 `04-counting-and-conversion.md` 第 3 节），**不是**按比例缩放得出。
3. 报告必须附**模块级明细表**（模块 / 功能点数 / 测试点数 / 用例数），作为可追溯证据。

## 9. 契约自检清单

- [ ] 是否所有用例都满足"可独立执行 + 可独立判定 + 单业务意图"？
- [ ] 是否存在"某字段必填校验"这类用例？（应为步骤，需合并）
- [ ] 聚合比是否落在 [1.5, 4.0]？（`check_consistency.py` 自动核）
- [ ] 每个测试点是否都至少被一条用例引用？（覆盖率 100%）
- [ ] 每条用例的 `point` 是否都能在 Spec Model 中找到？
- [ ] 去重差额是否在 `dedup_log` 中登记？
- [ ] 步骤与预期是否严格一一对应？
