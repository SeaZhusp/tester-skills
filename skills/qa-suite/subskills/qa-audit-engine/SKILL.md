## 0. 定位：三条职责

| 职责 | 触发信号 | 输入 | 输出 |
| --- | --- | --- | --- |
| **A. 一致性核销** | "核销 / 一致性 / 偏差 / 对不上" | Spec Model + 用例集 | 核销报告（覆盖率、偏差、缺失清单） |
| **B. 查漏与评审** | "评审 / 查漏 / 覆盖分析 / 补充用例" | 需求文档 + 用例集 | 缺失清单 + 补充建议 |
| **C. 校准回填** | "校准 / 偏差分析 / 修正参数" | 售前预估 + 实际交付 | 聚合比实测 + 参数修正建议 |

**边界**：本引擎只**报告**问题，**不擅自修改**口径、参数或产出。修改需由总控统一执行（遵守配置唯一契约）。

## 2. 职责 A · 一致性核销

### 执行

```bash
python3 "$SKILL_DIR/scripts/check_consistency.py" --estimate <spec-model.json> --cases <用例集.json>
python3 "$SKILL_DIR/scripts/validate_spec_model.py" <spec-model.json>
python3 "$SKILL_DIR/scripts/count_cases.py" <spec-model.json>
```

### 核销项（T1~T8，见 `07` 第 3 节）

| # | 核销项 | 门禁 |
| --- | --- | --- |
| T1 | 用例 `point` 全部可解析 | FAIL 即不合格 |
| T2 | 测试点覆盖率 = 100% | FAIL 即不合格 |
| T3 | 每个功能点至少 1 个测试点 | FAIL |
| T4 | 每个模块至少 1 条用例 | WARN |
| T5 | 用例 `module` 可匹配 | FAIL |
| T6 | 用例 `note` 非空且含需求引用 | FAIL |
| T7 | 模块覆盖率 ≥ 90% | FAIL（<90%） |
| T8 | 预估 vs 实际条数偏差 ≤ 20%（或已说明） | FAIL |

### 必附：双向核对表

| 模块 | 功能点数 | 测试点数 | 售前预估用例数 | 实际交付用例数 | 偏差 | 覆盖率 |
| --- | --- | --- | --- | --- | --- | --- |

偏差 = `(实际 − 预估) ÷ 预估`。偏差 > 20% 的模块**必须逐条说明原因**。

## 3. 职责 B · 查漏与评审

**独立视角**：不信任已有用例，从需求侧反向重建期望集合，再对比。

### 4 个查漏视角（对应 `01` 与 `02`）

| 视角 | 方法 | 典型缺失 |
| --- | --- | --- |
| **模块视角** | 逐模块核对功能点是否都有对应用例 | 整个模块漏做 |
| **状态机视角** | 每个业务对象的每条合法/非法转移是否都有用例 | 非法转移（越权/竞态）缺失 |
| **角色视角** | 每个角色 × 操作/越权是否覆盖 | 权限用例集中缺失 |
| **端到端场景视角** | 跨模块主链路是否作为 L0 冒烟用例 | 集成/契约/回滚用例缺失 |

### 输出要求

- **缺失清单**：需求点 → 缺失类型 → 建议补充的用例（写清模块、测试点、优先级）。
- **冗余清单**：疑过度拆分的用例（聚合比 < 1.5 的模块），给合并建议。
- **判定与建议分开**：明确哪些是"必须补"（覆盖率 < 100%）、哪些是"建议补"（增强覆盖）。

**优先检查两类极端**：聚合比 < 1.5 的模块（疑把校验维度单独成条）与 > 4.0 的模块（疑一条用例塞了多个业务意图）。
这两类最容易造成"覆盖率看起来很漂亮、执行成本完全失真"。

## 4. 职责 C · 校准回填（闭环）

### 步骤

1. **采集实测数据**：
   - 实测聚合比 = 实际测试点数 ÷ 实际交付用例数；
   - 实测 P0 占比、实测模块覆盖率、实测设计/执行工时（若可得）。
2. **对比预估**：与预估聚合比、参考分布、`assets/estimate-config.json` 参数逐一对比。
3. **偏差判定**：偏差 > 20% 视为显著。
4. **输出修正建议**（**不自动写入**）：
   - 聚合比偏低的模块 → 建议在 Spec Model 中合并场景；
   - 产能参数偏离实测 → 建议调整 `case_design_per_day` / `case_execution_per_day`；
   - 优先级分布偏离 → 建议复核 `05` 的推导规则。
5. **提交总控**：由总控确认后统一修改 `assets/`（配置唯一）。

### 校准记录表（建议长期留存）

| 批次 | 预估条数 | 实际交付 | 偏差 | 实测聚合比 | 实测人天 | 建议 |
| --- | --- | --- | --- | --- | --- | --- |

**这一步不可省**：不校准，参数永远是经验值；校准一次，后续每个项目都更准一分。

## 6. 严格禁止

| 禁止 | 原因 |
| --- | --- |
| 自行修改 Spec Model 或用例集 | 破坏唯一上游与只读原则 |
| 自行修改 `assets/` 参数 | 配置唯一契约 |
| 用"口头说明"替代 FAIL 登记 | 质量失控，必须显式登记 FAIL 项与残留风险 |
| 只报总数不报模块明细 | 不可追溯 |
| 把"建议补"混入"必须补" | 误导交付决策 |

## 7. 高发错误

| 错误 | 后果 |
| --- | --- |
| 只跑脚本不看内容 | 漏掉语义类缺失（脚本只能查结构） |
| 查漏时复用生成侧的逻辑 | 同源盲区，查不出系统性遗漏 |
| 校准建议直接改配置 | 违反契约，多处漂移 |
| FAIL 项只写"已沟通" | 无证据链 |
