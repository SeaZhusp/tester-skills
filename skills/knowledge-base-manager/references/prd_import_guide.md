# PRD 文档导入解析指南

## 概述

本指南定义了如何从不同格式的 PRD 文档中提取需求信息，结构化写入知识库。

## 核心原则（必须遵守）

### 原则0：业务逻辑是核心焦点

需求入库的**核心是业务逻辑**，其他内容都是辅助。业务逻辑包括：

- **业务流程**：功能从触发到结束的完整路径，谁做了什么、什么顺序、什么条件下流转
- **业务规则**：约束条件、校验逻辑、计算规则、状态转换条件、权限控制
- **前置条件**：功能可用的前提条件
- **业务术语**：该业务领域的专有名词和概念

> **入库时，优先确保业务流程和业务规则的完整准确**。UI 细节、交互样式、输入输出格式等属于实现层面的内容，不是核心关注点。如果 PRD 中的业务逻辑描述不清晰，必须追问用户直到搞清楚。

### 原则1：只写文档中有的，绝不编造

- **只基于 PRD 原文**：文档中写了什么就写什么，不要自行推测、补全或编造
- **没有明确的章节就不写**：例如 PRD 只写了业务描述，没有写业务规则，那生成的 REQ 文档就不要写"业务规则"章节
- **逐字引用优先**：对于关键规则、验收条件、业务流程，优先使用原文，可做格式整理但不要改变原意
- **合理推理 vs 编造的边界**：
  - ✅ 允许：将原文"密码错误时提示'账号或密码错误'"整理为验收标准格式
  - ❌ 禁止：原文没写验证码规则，自行编造"验证码有效期5分钟"

### 原则2：信息不足时反问用户

当以下情况发生时，**必须停下来反问用户**，不要自行决定：

- **模块归属不明确**：PRD 中的某个功能不知道属于哪个模块 → 问用户
- **缺失关键信息**：
  - 业务流程只有标题没有步骤描述 → "这个流程的具体步骤是什么？"
  - 提到了规则但没有具体约束值 → "密码长度限制是多少？"
  - 验收标准只有一句话 → "还有哪些验收条件？"
- **需求命名不确定**：PRD 没有明确的标题 → "这个功能应该叫什么名字？"
- **关联关系不清**：某个接口明显对应某个需求，但 PRD 没写明 → 问用户确认

反问不是一次性完成，而是**逐轮交互**——问清楚一个再继续。

### 原则3：一次只入库一个模块

- PRD 可能覆盖多个功能模块，**不要一次性全部入库**
- **先与 PRD 确认模块数量**："我看到这个 PRD 涉及了 XX 和 XX 两个模块，先处理哪个？"
- **用户确认后再处理单一模块**：选定模块 → 解析该模块内容 → 生成文档 → 用户确认 → 入库
- **完成后问用户是否继续**：当前模块入库后，再处理下一个模块

### 原则4：业务逻辑不清时优先追问

当 PRD 中对业务逻辑的描述不够清晰时，必须追问用户。以下场景尤其需要追问：

- **业务流程路径不完整**：只写了"用户登录成功"，没写失败怎么处理
- **规则值缺失**：写了"密码有复杂度要求"，没写具体要求
- **状态流转不明确**：写了订单有多种状态，没写状态之间的转换条件和触发动作
- **分支条件模糊**：写了"某些情况下需要审批"，没写具体什么情况

## 支持的输入格式

| 格式 | 读取方式 | 注意事项 |
|------|---------|---------|
| `.docx` | `docx` skill 或 `python-docx` 库 | 关注标题层级、表格、列表 |
| `.pdf` | `pdf` skill 或 `PyMuPDF`/`pdfplumber` | 表格可能被拆分，需人工整理 |
| `.md` | 直接读取 Markdown | 结构最清晰，可直接提取 |
| 图片(.png/.jpg) | 大模型视觉识别能力 | 适合流程图、原型截图 |
| `.txt` | 直接读取 | 缺乏结构，需充分补全 |

## 解析流程

### Step 1：读取文档内容

根据不同格式采用不同的策略：

**docx 文档解析要点**：
- 读取所有段落文本和格式信息
- 提取表格内容（table rows/cells）
- 识别标题层级（Heading 1/2/3 对应不同的章节级别）
- 提取列表中嵌套关系
- 保留图片中的文本（如果流程图是嵌入图片，通过视觉识别）

**pdf 文档解析要点**：
- 按页面顺序提取文本
- 关注表格结构（pdfplumber 对表格支持较好）
- 注意段落合并，避免跨页断开
- 流程图如果作为图片嵌入，通过视觉识别

**图片（流程图/原型截图）解析要点**：
- 流程图：通过视觉能力识别流程节点、分支、箭头方向
- UI 原型图：识别页面元素、交互路径
- 表格截图：识别行、列、单元格内容

### Step 2：结构化信息提取

从 PRD 文档中提取以下信息维度（**业务逻辑相关的内容优先提取，没有的不要硬写**）：

| PRD 原文内容 | 映射到知识库位置 | 优先级 |
|-------------|----------------|--------|
| 项目背景/产品背景 | REQ-xxx → 业务概述 section | 中 |
| **业务流程**（流程图、步骤描述、状态迁移） | REQ-xxx → 业务流程 section | **高** |
| **业务规则/约束条件**（校验规则、计算公式、权限控制） | REQ-xxx → 业务规则表（RULE） | **高** |
| **前置条件**（先决条件、前置状态） | REQ-xxx → 前置条件 | **高** |
| 用户故事/场景描述 | REQ-xxx → 业务流程 section | 中 |
| 功能列表 | 拆分为多个 REQ，或作为模块列表 | 中 |
| 字段定义 | REQ-xxx → 输入/输出规格表（可选章节） | 低 |
| 验收条件 | REQ-xxx → 验收标准 | 中 |
| 术语定义 | `_glossary.md` | 中 |
| 架构描述 | `_architecture.md` | 低 |
| 流程图/时序图 | REQ-xxx → 业务流程（描述文字替代） | 高 |

> **优先级说明**：高=必须提取，信息不完整必须追问；中=有则写没有不写；低=仅当 PRD 中有明确定义时填写

> **注意**：如果 PRD 中没有对应的内容，对应的 section 就不写。
> 例如 PRD 只描述了业务背景和规则，没有写验收标准 → 生成的 REQ 就不写"验收标准"章节。
> 千万不要自己编造验收条件。

### Step 3：按模块逐一处理（一次只处理一个模块）

一个 PRD 可能涉及多个模块。处理流程如下：

1. **先识别模块数量**：读取完整 PRD 后，识别涉及的所有模块
2. **列出模块给用户确认**：
   ```
   我识别到这个 PRD 涉及以下模块：
   - user-auth（用户认证）
   - payment（支付）
   
   先处理哪一个？还是两个模块都涉及到了？
   ```
3. **用户选定后只处理该模块**：
   - 从 PRD 中只提取选定模块的内容
   - 生成该模块的 _overview.md 和 REQ-*.md
4. **完成后问用户**："user-auth 模块的文档已经入库了。需要继续处理 payment 模块吗？"

### Step 4：ID 分配与版本

- 使用 `REQ-{三位数}` 命名，从已存在的最大 ID 后继续
- 从 PRD 文件名或内容中提取版本号，填入 `version`
- 如果没有版本号，**反问用户**："这个 PRD 的版本号是多少？暂定 v1.0 是否可以？"

### Step 5：用户确认（逐轮确认）

在写入知识库前，**逐项**向用户呈现并确认：

1. **这个功能的名称是否正确？** → 用户可调整
2. **业务描述是否准确？** → 展示提取的概述
3. **是否有遗漏的业务规则？** → 展示提取的规则表
4. **验收标准是否完整？** → 展示提取的验收标准
5. **还有什么需要补充的？** → 询问用户

### Step 6：入库后

1. 调用 `scripts/update_index.py` 更新索引
2. 在 `_upgrade_log.md` 记录本次操作
3. 输出入库摘要：
   ```
   ✅ user-auth 模块入库完成！
   源文件：用户认证PRD_v1.2.docx（已保存在 _source/）
   生成需求：
   - REQ-001 用户登录功能（基于 PRD 第3-5页）
   
   还有 payment 模块待处理，是否继续？
   ```

## 常见 PRD 内容模式识别

### 模式1：章节式 PRD（按功能模块分章节）

```
1. 用户注册功能
   1.1 业务描述
   1.2 业务流程
   1.3 规则约束
2. 用户登录功能
   2.1 ...
```

→ 先让用户确认按几个模块入库。如全部为同一模块则直接处理，否则按 Step 3 逐一处理。

### 模式2：用户故事式 PRD

```
As a 用户
I want 登录系统
So that 进入首页

Acceptance Criteria:
1. 输入正确账号密码能登录
2. 输入错误密码显示提示
```

→ 每个用户故事生成一个 REQ，AC 映射到验收标准。AC 中有的就写，没有的就跳过。

### 模式3：原型标注式 PRD

文字描述较少，以原型图/UI 截图为主，辅助标注文字。

→ 通过视觉识别逐页面提取功能点
→ **信息不足时反问**：这个页面的业务规则是什么？这个交互的触发条件是什么？

### 模式4：接口式 PRD

简单描述 + 完整的接口定义表格。

→ 接口部分拆分为单独的 `API-*.md` 存入 `02-api-docs/`
→ 功能描述部分生成 `REQ-*.md`
→ 接口表格中有的字段就写，没有的字段不写

## 文档模板中的 `source` 字段

在 `doc_templates.md` 的需求文档模板 frontmatter 中增加 `source` 字段：

```yaml
---
source: 用户认证PRD_v1.2.docx  # 指向 _source/ 中的原始文件名
source_page: 3-8              # 可选：源文件中的页码范围
---
```

## 后处理

导入完成后：
1. 调用 `scripts/update_index.py` 更新索引
2. 在 `_upgrade_log.md` 记录：`导入 PRD {文件名} → 生成 REQ-xxx, REQ-xxx 共N个需求`
3. 输出入库摘要给用户：
   ```
   ✅ 入库完成！
   源文件：用户认证PRD_v1.2.docx（已保存在 _source/）
   生成需求：
   - REQ-001 用户登录功能（user-auth）
   新增术语：Token（已在 glossary 中记录）
   ```
